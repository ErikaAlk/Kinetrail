# 沃莱 P3 的 BLE 协议与体成分算法

ICOMON 沃莱 P3（双频八电极体脂秤，配 FitDays / FitDays+）的直连方案实测记录。目标是绕开
「必须在 FitDays+ 里打开测量页、看到动画才写 Health Connect」这条链路（`HEALTHCONNECT.md`
第 6 节），让每一次称重都能进 Kinetrail，并且拿到比 Health Connect 更底层的 10 个原始阻抗。

**本文的帧和数值都是合成的**，结构与真实一致，读数不是真人的（仓库公开，见 `CLAUDE.md`
「只存本人」与提交纪律）。

起点是 [sacoma-lib](https://github.com/ynsgnr/sacoma-lib)（MIT），它逆的是 SACOMA Ultra——
同为 ICOMON/Chipsea 八电极秤的另一个贴牌。P3 与它同协议族，但帧信封和结果消息都不一样。

## 1. 传输层

GATT 服务 `FFB0`：`FFB1` 写命令、`FFB2` notify（实时体重）、`FFB3` indicate（结果与状态）。
明文，无加密。**只读不写就能拿到全部数据**——实测在一个字节都没写出去的情况下，秤自己推送了
实时体重流和最终结果。代价是秤自己屏幕上那 6 个体成分值会显示 `--`，因为没有 App 在喂心跳。

帧是变长的（Ultra 是定长 20 字节补齐）：

```
[0]      序号（0..255，回绕）
[1:3]    载荷长度（u16 大端）
[3]      分片序号（0, 1, ...）
[4:-1]   载荷
[-1]     校验和 = sum(载荷) & 0x1F
```

校验和规则与 Ultra 相同。实测 MTU 协商后单帧就能装下 35 字节的结果载荷，没见过分片，但
长度字段是 16 位，分片字段也在，所以重组逻辑要留着。

## 2. 秤 → App 的消息

载荷第 0 字节是类型。

### `A2` 实时体重（FFB2）

```
[0]    0xA2
[1]    状态  0x01 实时 / 0x03 稳定 / 0x00 已出结果
[2]    0x00（Ultra 在这里放算法号）
[3:6]  体重 u24 大端，单位克
[6]    0x00
```

载荷布局与 Ultra 完全一致，sacoma 的 `decode_message` 原样可用。

### `A7` 测量结果（FFB3）

```
[0]     0xA7
[1:5]   时间戳 u32 大端
[5]     算法号（见第 4 节）
[6:9]   体重 u24 大端，单位克
[9]     0x00
[10]    阻抗个数（P3 是 10）
[11:]   个数 × u16 大端，除以 10 得欧姆
[后面]  4 字节用途未知
```

Ultra 用的是 `A3`，没有时间戳，体重在 `[2:5]`。

**体重必须按 u24 读。** 单次实测数据里 u16 和 u24 恰好同值，容易误判；65.535 kg 以上 u16
就会溢出。

阻抗排布与 Ultra 同构：第 0 位小、1–4 位大、第 5 位小、6–9 位大，即双频 ×（躯干 + 四肢）。
段位到肢体的具体映射没有单独验证，但按原顺序喂给算法能精确复现 App 的分段结果，说明顺序对。

### 两条要当心的

- **帧里的时间戳信不得。** 实测秤的 RTC 与真实时间差了约 15 小时——平时由 App 在同步时校时，
  纯只读连接不会校。入库一律用收到的时刻。
- **A7 里没有用户标识。** 谁站上去都是同一种帧。多成员家庭只能靠体重区间区分人，区间重叠就会
  串号。Kinetrail 的「只存本人」是硬不变量，这里宁可漏收也不能错收。

## 3. 解码

`p3/decode.py` 是不依赖任何第三方库的解码器，自带合成帧自检：

```bash
python research/p3/decode.py
```

`p3/probe.py` 是现场探针：打印完整 GATT 服务表，订阅所有可通知的特征，把原始字节和校验和的
对错一起打出来。查「秤到底推了什么」用它。

## 4. 体成分算法

> 算法本身怎么工作的——阻抗如何变成那几十项、哪些是真测的哪些是算的——见
> [P3-ALGORITHM.md](P3-ALGORITHM.md)。本节只记逆向和调用的事实。

秤只上报体重和阻抗，其余全部由 App 算。算法在 `libICBodyFatAlgorithms.so`
（`split_config.arm64_v8a.apk`，`adb shell pm path cn.icomon.fitdayspro` 取得，不需要 root），
里面有 43 个 `ICBodyFatAlgorithmWLA07..WLA44` 类。

**A7 载荷 `[5]` 就是 WLA 编号。** P3 是 `0x25` = 37 → `WLA37`。旁证：Ultra 的 A3 在对应位置是
`0x19` = 25，而 sacoma 逆出来的正是 `WLA25`。

> 注意 Java 枚举 `ICBodyFatAlgorithmsType` 的序号比名字小 1（`WLA37(36)`），传给
> `native_calc` 的 `algType` 要用 **36**，不是 37。

### 怎么调

JNI 入口 `native_calc` 收字符串键的 `HashMap`，不是结构体，所以没有 ABI 要摸：

| 键 | 类型 |
| --- | --- |
| `weight` | Double（kg） |
| `height` | Integer（cm） |
| `age` | Integer |
| `sex` | Integer（1 = 男） |
| `algType` | Integer（P3 = 36） |
| `peopleType` | Integer（0 普通 / 1 运动员） |
| `standard` `enableGirth` | Integer |
| `imp1`..`imp5` | Double（前五个阻抗） |
| `imps` `impCount` | List&lt;Double&gt; 与个数 |

返回的 map 有 70 多个字段，含 App 界面上没显示的 `bmr`、`bodyScore`、`whr`、`smi`、
`obesityDegree`、以及各段的脂肪/肌肉质量与百分比。

**坑：native 会回调 Java 的 `getKeysFromMap` 和 `getObjectType` 来遍历那个 map。** 调用方的壳类
必须同包同名（`com.icomon.icbodyfatalgorithms.ICBodyFatAlgorithms`）并实现这两个静态方法，
否则返回的 map 字段齐全但**全是零，且不抛异常**，很容易误判成参数错。

`p3/algorithm/` 下是最小调用壳和跑法，不需要 root、不需要装 App。

### 纯 Python 实现

`p3/wla37.py` 不依赖 `.so`，任何平台都能跑。它由 sacoma-lib 的 `wla25.py`（MIT）机械改写
而来：把两边的反编译结果各自代入 .rodata 常数、归一化变量名后逐行比对，1078 行里只有两处
语义差异——体脂核心（WLA25 内联 13 项回归，WLA37 改调 `calcBF`：27 项线性回归，系数表按
`(前五个阻抗之和 / 身高)` 分 <9 / 9-12 / >=12 三档），以及校验门限（身高 [100,220] →
[100,260]，体重 [20,200] → [20,260]）。其余全部原样保留。出处与许可见
`p3/NOTICE-sacoma-lib.md`。

对账拿设备算法库当基准：`algorithm/Vectors.java` 在真机上跑一个合成输入网格，
`p3/wla37-vectors.jsonl` 是导出的参考向量，`p3/check_wla37.py` 逐项比对。

```bash
python research/p3/check_wla37.py
```

**实测 192 条向量 / 6144 个数值全部一致**，最大偏差 1.7e-13（float64 尾数噪声）。生成时
用的完整网格是 768 条 / 24576 个数值，同样零不一致。

### 实测结论

用真机上一次真实称重的帧，按 `algType=36`、`sex=1` 调用，与 FitDays+ 界面逐项核对：
BMI、体脂率、肌肉率、皮下脂肪、内脏脂肪、身体水、骨骼肌、骨重量八项全部一致到显示精度，
四肢与躯干的脂肪百分比和质量也全部一致。扫过 `algType` 0..60 × 性别 × 体型，只有 36 是精确解，
次优的 33 差 0.8。

作为对照：用 Ultra 的 `WLA25` 硬算同一组数据，BMI、内脏脂肪、骨重量三项恰好相同，其余五项呈
「脂肪偏低、瘦体偏高」的同向偏差（体脂率差 1.4 个百分点）；穷举 48 种阻抗段位排列最好也只能
把误差压到一半。所以确实是系数集不同，不是顺序问题。

## 5. `.so` 的运行环境

`DT_NEEDED` 是 `liblog/libm/libdl/libc`——**bionic**，不依赖 `libc++_shared.so`。在 glibc 机器上
直接 `dlopen` 不行：glibc 的 `libc.so` 是链接脚本，`liblog.so` 根本不存在。

未定义符号里 bionic 专有的只有四个：`__errno`、`__sF`、`__system_property_get`、
`android_set_abort_message`，其余都是标准 C/POSIX。所以在 glibc 上补一层垫片是可行的，
`__sF`（bionic 的 `FILE` 数组，布局与 glibc 不同）是唯一有风险的一个，只在出错路径上用到。
**未验证。**

`.so` 是沃莱的，不在本仓库里，自己从 FitDays+ 的 APK 取。

## 6. 还没做的

- 网关本身：常驻连秤、解 A7、算指标、推 Kinetrail。
- 服务端契约：现在 `HC_ORIGIN` 是常量、schema 里 `origin` 用 `const` 锁死、
  `source_record_id` 形如 `hc:<包名>:<time_ms>`、识图报告只能挂到已入库的 HC 称重上。
  新增 BLE 来源是 `DATA_CONTRACT.md` 第 8 节级别的改动。
- `wla37.py` 沿用了 sacoma 的两处未移植部分：18 岁以下的标准 BMI 身高树（会抛
  `NotImplementedError`），以及 WHR。本人用不到，接别人之前要补。
- 写命令（`BA` 心跳等）在 P3 上的帧格式没验证过。只读不需要它。
